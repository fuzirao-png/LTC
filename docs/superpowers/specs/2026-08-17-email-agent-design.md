# Email Agent 设计说明

## 1. 背景

LTC 客户运营模块已经具备邮件草稿生成、正文翻译、人工编辑和邮件发送能力。后端已有 `email_generate`、`email_translate` Skill、`SKILL_REGISTRY`、邮件上下文构建器和邮件发送服务；前端已有 `EmailComposer`，包含联系人选择、优化指令、主题、正文、翻译结果和发送操作。

本设计不重做邮件系统，而是在现有能力之上增加统一的邮件编辑 Agent。Agent 的正式名称为 `email-agent`。

## 2. 目标

第一阶段将现有邮件编辑能力转化为可扩展的 Agent 编排能力，使用户能够在现有邮件编辑器中：

1. 根据客户上下文生成邮件；
2. 优化现有邮件；
3. 翻译邮件；
4. 使用自然语言指令改写邮件；
5. 预览 Agent 结果，并在人工确认后应用到编辑器；
6. 后续通过注册新 Skill 扩展能力，而不为每个 Skill 新建页面或独立前端流程。

## 3. 已确认的产品约束

- 入口继续使用现有 `EmailComposer`；
- 不新增独立聊天页或侧边 Agent 面板；
- 采用固定按钮与自然语言指令结合的交互方式；
- 第一阶段不增加独立的“优化邮件”按钮；
- 现有“优化指令”输入框作为自然语言指令入口；
- Agent 结果不得直接覆盖当前主题或正文；
- 用户确认后才应用 Agent 结果；
- 邮件发送继续由用户手动触发；
- 不进行页面布局或视觉风格调整；
- 任何后续前端视觉、文案、按钮或交互微调，实施前必须再次获得用户确认。

## 4. 方案选择

采用统一 Agent 入口方案：前端向 `email-agent` 提交当前草稿、用户指令和客户标识，由 Agent 构建上下文、选择 Skill、执行编排并返回待确认结果。

未采用以下方案：

- 前端直接调用所有独立 Skill 接口：扩展 Skill 时会持续增加前端耦合；
- 第一阶段引入通用多 Agent 工作流框架：复杂度超过当前邮件编辑场景的需要。

## 5. 系统边界

### 5.1 `email-agent` 负责

- 校验调用参数和用户访问权限；
- 读取当前客户、联系人及相关运营上下文；
- 合并当前主题、正文和自然语言指令；
- 根据固定操作或自然语言意图选择 Skill；
- 按顺序执行一个或多个 Skill；
- 校验 Skill 输出；
- 返回待确认的邮件版本和执行元数据；
- 记录必要的调用审计信息。

### 5.2 `email-agent` 不负责

- 自动选择收件人；
- 自动发送邮件；
- 定时或批量发送营销邮件；
- 自动创建跟进任务；
- 修改客户或联系人资料；
- 修改历史邮件；
- 直接覆盖用户当前草稿；
- 自主调用未注册或未授权的 Skill；
- 在第一阶段维护长期聊天会话或草稿版本历史。

## 6. 总体架构

```text
EmailComposer
    ↓
Email Agent API
    ↓
email-agent
    ├── 权限校验
    ├── 上下文构建
    ├── 操作与意图路由
    ├── Skill 编排
    ├── 输出校验
    └── 调用审计
          ↓
    SKILL_REGISTRY
        ├── email_generate
        ├── email_optimize
        ├── email_translate
        └── email_rewrite
          ↓
Draft Review Result
    ↓
用户确认后应用到编辑器
```

`email-agent` 属于客户运营模块的应用层编排能力。Skill 负责单项邮件处理能力，基础设施适配器继续负责模型调用、数据库读取和邮件发送。

## 7. API 设计

### 7.1 新增统一接口

```text
POST /customer-operation/email/agent
```

### 7.2 请求结构

```json
{
  "companyId": "company-id",
  "contactId": "contact-id",
  "subject": "当前主题，可为空",
  "body": "当前正文，可为空",
  "instruction": "请突出我们在东南亚的交付能力",
  "operation": "rewrite",
  "targetLanguage": "English"
}
```

字段规则：

- `companyId` 和 `contactId` 用于权限校验和上下文读取；
- `subject`、`body` 表示当前编辑器草稿；
- `instruction` 表示用户自然语言要求；
- `operation` 仅允许 `generate`、`optimize`、`translate`、`rewrite`；
- `targetLanguage` 在翻译操作中必填，其他操作可为空；
- `optimize`、`translate`、`rewrite` 要求当前主题或正文至少存在一项；
- 自由改写要求 `instruction` 非空。

### 7.3 响应结构

```json
{
  "success": true,
  "agent": "email-agent",
  "operation": "rewrite",
  "subject": "优化后的主题",
  "body": "优化后的正文",
  "language": "English",
  "skills": ["email_rewrite"],
  "changes": [
    "调整为更正式的商务语气",
    "突出东南亚交付经验"
  ],
  "model": "model-name",
  "message": "邮件草稿已生成，请确认后使用"
}
```

`skills` 使用列表而不是单个字符串，以支持自然语言指令按顺序调用多个 Skill。

## 8. Skill 设计

### 8.1 第一阶段 Skill

```python
SKILL_REGISTRY = {
    "email_generate": EmailGenerateSkill(),
    "email_optimize": EmailOptimizeSkill(),
    "email_translate": EmailTranslateSkill(),
    "email_rewrite": EmailRewriteSkill(),
}
```

- `email_generate`：根据客户上下文和用户要求生成完整主题与正文；
- `email_optimize`：在保留原意和关键事实的前提下优化语气、结构、表达和 CTA；
- `email_translate`：翻译主题和正文，不额外增加原文没有的业务事实；
- `email_rewrite`：根据自然语言指令对主题和正文进行定向改写。

### 8.2 统一 Skill 输出

所有邮件 Skill 返回统一结构：

```python
{
    "subject": str,
    "body": str,
    "language": str | None,
    "changes": list[str],
    "model": str,
}
```

输出校验至少包括：

- `subject` 和 `body` 类型正确；
- 操作要求生成正文时，`body` 不得为空；
- `changes` 必须为字符串列表；
- 输出不得包含发送指令或绕过人工确认的动作；
- 模型返回格式不符合契约时，整个 Agent 请求失败。

### 8.3 Skill 扩展流程

后续增加 Skill 时需要：

1. 实现符合统一输入输出契约的 Skill；
2. 注册到 `SKILL_REGISTRY`；
3. 在 `email-agent` 路由规则中声明适用操作或意图；
4. 增加 Skill 单元测试和 Agent 路由测试；
5. 如果 Skill 需要新增前端入口或视觉反馈，必须先获得用户确认。

## 9. 路由与编排规则

### 9.1 固定操作

固定操作优先使用明确路由，不让模型自由选择：

```text
generate  → email_generate
optimize  → email_optimize
translate → email_translate
```

### 9.2 自然语言改写

`rewrite` 由 `email-agent` 分析指令并选择一个或多个 Skill。例如：

```text
“再正式一点，突出东南亚交付经验”
→ email_rewrite

“翻译成英文并缩短一些”
→ email_translate
→ email_rewrite
```

多 Skill 编排按声明顺序执行。任一 Skill 失败后立即停止，不返回未经完整处理的结果。

第一阶段不采用开放式工具循环。Agent 只能从邮件 Skill 白名单中选择能力，并设置最大调用步数，避免循环调用和不可控行为。

## 10. 客户上下文

`email-agent` 复用并扩展现有邮件上下文构建能力，按需读取：

- 当前客户基础信息；
- 当前联系人姓名、职位和邮箱；
- 公司行业、地区和规模等资料；
- 当前运营阶段；
- 与当前联系人相关的近期往来邮件；
- 已提取的会议摘要和客户需求；
- 当前编辑器主题、正文和用户指令。

上下文必须裁剪：

- 只读取当前用户有权访问的数据；
- 优先读取与当前联系人直接相关的记录；
- 默认限制历史邮件数量；
- 长内容使用摘要或关键事实；
- 排除无关联系人和其他销售人员的数据；
- 不把邮箱凭证、Token、密码或提供商密钥发送给模型。

## 11. 会话与记忆

第一阶段采用请求级记忆：

- 当前主题和正文继续由前端状态保存；
- 每次请求携带最新主题、正文和用户指令；
- 客户历史从现有数据库读取；
- `email-agent` 不建立长期会话；
- 不新增 Agent 会话表；
- 不新增草稿版本表或数据库迁移。

## 12. 前端接入

第一阶段复用现有 `EmailComposer`，不改变页面布局和视觉风格。

操作映射：

```text
正文为空 + 点击“生成草稿”
→ operation = generate

正文已有内容 + 填写优化指令 + 点击“生成草稿”
→ operation = rewrite

正文已有内容 + 点击“翻译正文”
→ operation = translate
```

Agent 返回结果后：

- 不立即修改当前 `subject` 或 `body`；
- 使用现有结果展示能力呈现待确认版本；
- 用户点击确认操作后才应用主题和正文；
- 用户取消时保留当前草稿；
- 发送按钮继续调用原有发送流程。

如果实现待确认主题需要改变现有文案、按钮或结果区域行为，必须先向用户说明具体微调并获得批准后才能实施。

## 13. 权限与安全

每次调用必须：

1. 获取当前登录用户；
2. 校验用户是否有权访问 `companyId`；
3. 校验 `contactId` 属于该客户；
4. 仅读取该用户有权访问的客户、邮件和会议资料；
5. 将用户自然语言指令视为内容，不允许其绕过权限或调用非白名单工具；
6. 禁止 Skill 调用邮件发送能力；
7. 禁止在普通日志中记录邮箱密码、Token、密钥或完整敏感凭证。

## 14. 内容可靠性

Agent 和 Skill 必须遵守：

- 不虚构价格、案例、客户、认证或交付能力；
- 用户要求与已知客户事实冲突时，以已知事实为准；
- 信息不足时使用保守表达，不把推断表述为事实；
- 翻译不得自行增加业务承诺；
- 优化和改写默认保留原文核心事实；
- 客户上下文不足时可以生成通用邮件，但不得补造客户细节。

## 15. 兼容策略

现有接口暂时保留：

```text
POST /email/generate
POST /email/translate
```

兼容方式：

- 第一阶段不删除旧接口；
- 新版 `EmailComposer` 使用统一 Agent 接口；
- 旧接口可以逐步在内部委托给 `email-agent`；
- 邮件发送接口和发送服务不纳入 Agent 编排；
- 原有调用方在迁移完成前继续可用。

## 16. 错误处理

- 客户或联系人无权限：拒绝请求，不调用模型；
- `companyId` 与 `contactId` 关系无效：拒绝请求；
- 自由改写指令为空：返回参数错误；
- 当前正文为空且执行优化或翻译：返回参数错误；
- 模型或 Skill 调用失败：保留原草稿并返回可理解的错误；
- Skill 输出不符合契约：视为失败，不应用结果；
- 多 Skill 链路失败：停止后续步骤，不返回部分成功结果；
- 客户上下文不足：允许生成通用草稿，并在调用元数据中记录上下文不足。

## 17. 审计与可观测性

每次 Agent 调用记录：

- `agent_name = email-agent`；
- 当前用户 ID；
- 公司 ID 和联系人 ID；
- 请求操作类型；
- 实际调用的 Skill 列表；
- 模型名称；
- 调用耗时；
- 成功或失败状态；
- 结构化错误类型。

普通日志默认不保存完整邮件主题、正文和客户敏感上下文。需要问题排查时，应使用受控的调试机制，而不是长期记录明文内容。

## 18. 测试策略

### 18.1 后端测试

- 固定操作正确路由到对应 Skill；
- 自然语言指令能够路由到单个或多个 Skill；
- Skill 按声明顺序执行；
- 任一 Skill 失败时停止链路；
- 输出契约校验失败时拒绝结果；
- 无权限用户不能读取客户上下文；
- 联系人不属于客户时拒绝请求；
- 上下文构建只包含授权数据；
- Agent 不调用邮件发送能力；
- 旧生成和翻译接口保持兼容。

### 18.2 前端测试

- 当前草稿不会被 Agent 响应自动覆盖；
- 用户确认后才应用结果；
- 用户取消后原草稿保持不变；
- 有正文和优化指令时使用 `rewrite`；
- 无正文时使用 `generate`；
- 翻译操作使用 `translate`；
- Agent 请求失败时保留当前草稿并展示错误；
- 原有发送流程继续工作；
- 前端通过类型检查和生产构建。

## 19. 验收标准

1. 用户可以从现有邮件编辑器生成邮件；
2. 用户可以输入自然语言优化指令；
3. Agent 可以根据当前草稿和指令完成优化或改写；
4. 用户可以翻译邮件；
5. Agent 默认读取经过权限校验和裁剪的客户上下文；
6. Agent 结果不会自动覆盖当前草稿；
7. 用户确认后才应用主题或正文；
8. Agent 不会自动发送邮件；
9. 新 Skill 可以通过 Registry 和统一契约接入；
10. 无权限用户不能读取或使用客户邮件上下文；
11. 原有邮件发送能力继续正常工作；
12. 后端测试、前端类型检查和生产构建通过。

## 20. 第一阶段不包含

- 自动或定时发送邮件；
- 批量营销邮件；
- 邮件序列和自动跟进；
- Agent 自动选择收件人；
- 独立聊天页面或侧边栏；
- 长期 Agent 对话记忆；
- 草稿版本历史；
- A/B 测试；
- 页面布局和视觉风格调整；
- 未经用户批准的任何前端微调。
