## 1. 当前实现阶段

本轮建立 Web、API、Worker、PostgreSQL、契约测试和本地初始化入口，不伪装成已经完成业务 Use Case。

已经落地的工程边界：

- `apps/web/`：Vue 3 分层目录、路由与统一 API Client
- `apps/api/`：FastAPI 模块化单体目录、模块/平台表归属注册表、健康检查
- `apps/worker/`：Application Use Case 驱动的 Runtime 骨架
- `db/`：经审查的 v3.6 42 表 Migration 与区域国家 v5 Seed
- `contracts/`：OpenAPI 契约和受控基线文件校验清单
- `tests/`：架构、契约和数据库不变量测试
- `compose.yaml`：本地与 CI 的统一 Docker 运行/验收入口

当前 Worker 尚未接通 Job Repository 和常驻 Claim Loop，因此 Compose 只提供 Worker 测试镜像，不启动空的 Worker 服务。真实 Composition Root 完成后再把它加入常驻运行拓扑。

当前已接通的 Worker 处理边界只有三类：

- `lead.search_pipeline.v1`
- `platform.dispatch_outbox.v1`
- `platform.process_external_event.v1`

这三个 Handler 都只负责：

- 接收 `JobLease`
- 启动/结束 `job_attempt`
- 调用对应 Application Use Case
- 按 `LeaseLost / RetryableError / final failure` 走统一回写

当前**故意不创建**以下业务 Handler 文件，因为它们依赖的 API、Use Case、领域模型和 Provider 还未在新目录完成，先建只会制造伪实现：

## 3. Worker 边界

Handler 必须遵守以下规则：

- Handler 只能调 Application Use Case，不调 FastAPI Route
- Handler 不直接操作其他模块 ORM / Repository
- Provider 调用和长计算必须在数据库事务外
- `LeaseLost` 后不得继续回写
- Job 只保存技术态，业务结果必须写领域表
- Retry 必须通过 `jobs.retry(...)` 新建 Job，不能复活旧 Job

## 4. 当前范围约束

以下范围约束在 Worker 和未来 API 目录里都不能遗漏：

- 账号类型只有 `Sales/Strategic`
- 当前 `scene_code` 只有 `S1/S2/S3`
- Apollo 只允许作为内部 Provider，不允许独立 API 入口
- `Disable` 只影响登录，不释放客户
- `Depart` 和完整销售管理不是一回事
- 当前不实现 `Manager/Boss`
- 当前不实现 `S4/S5`
- 当前不实现跨 Region、跨 Tier、超 Capacity override
- 当前不实现 `handover_request`、审批、交接待办、等级调整

## 5. 运行验收

工程基线的完整验收从仓库根目录执行：

```bash
make test
```

通过标准：

- API/Worker 模块可编译且测试通过
- Web 类型检查和生产构建通过
- PostgreSQL 16 中完成 Migration、重复 Seed、并发竞争与 dump/restore 测试
- 架构、SQL、Seed、OpenAPI 受控基线的校验和无非预期漂移
- Registry 只暴露当前阶段 3 个 job type
- Runtime 能把 Job 分发到对应 Use Case
- Handler 源码不 import FastAPI
- 未提前创建未接通的业务 Handler 文件

1. `apps/api` 的 `platform.jobs`、`lead_search` Application Use Case

5. `email_*` 与 `manual_note_extract`
