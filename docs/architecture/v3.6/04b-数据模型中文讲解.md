## 二、IAM（身份与权限）— 2 张表

### 2.1 `user_account` — 用户账户

**用途**：存所有能登录系统的人，以及他们的销售等级、区域、容量。

| 字段 | 中文 | 业务含义 |
|------|------|----------|
| `user_id` | 用户ID | 全局唯一的用户标识，UUID |
| `username` | 登录名 | 登录时输入的用户名，全局唯一 |
| `password_hash` | 密码哈希 | 用 Argon2id 算法加密，不存明文 |
| `display_name` | 展示名 | 界面上显示的名字 |
| `email` | 账户邮箱 | 可选，用于找回密码等 |
| `account_type` | 账户类型 | 只有两种：`sales`（销售）或 `strategic`（战略人员） |
| `sales_tier` | 销售等级 | Sales 才有。MA=大客户销售、SA=中客户销售、A=普通销售 |
| `region_code` | 区域代码 | Sales 才有。NA=北美、EA=东亚、SEA=东南亚、EU=欧洲、ME=中东（v3.3新增）、OTHER=其他 |
| `capacity_limit` | 容量上限 | 最多同时跟多少个客户。推荐 MA=15、SA=25、A=40 |
| `status` | 账户状态 | active=正常、disabled=安全禁用、departed=已离职；临时登录锁不写入本列 |
| `failed_login_attempts` | 连续密码失败次数 | **v3.5新增**：连续输错密码的次数，登录成功即清零 |
| `locked_until` | 锁定期满时间 | 连续 5 次失败后锁定 30 分钟，不改变 account status |
| `departed_at` | 离职时间 | Strategic 成功执行离职命令的时间 |
| `departed_by` | 离职操作人 | 执行离职的 Strategic 用户 |
| `departure_reason` | 离职原因 | departed 时必填 |
| `token_version` | Token版本 | 数字递增，想强制所有人重新登录就 +1 |
| `last_login_at` | 最近登录时间 | 什么时候最后一次登录 |
| `version` | 乐观锁版本 | 每次修改 +1，防止并发冲突 |
| `created_at` | 创建时间 | 账户什么时候创建的 |
| `updated_at` | 更新时间 | 最后修改时间 |

⚡ **关键规则**：
- Sales 必须有 tier、region、capacity；Strategic 这三个字段为空
- 登录锁定只更新 `locked_until/failed_login_attempts`，不会把 disabled/departed 错误恢复为 active
- `status=departed` 后立即失去登录权限，全部 active Assignment 在同一事务结束，Lead 保留原区域×等级及规则版本快照并回 claimable 池
- Disabled 只撤销登录和 Session，不释放客户、不清任务、不取消业务 Job
- active/disabled Sales 都能由 Strategic 执行 Depart；departed 当前是终态，不能通过通用 Enable 恢复

### 2.1b `sales_tier_history` — 等级变更历史（v3.3 新增，v3.5 起 Deferred，暂不做）

> **Deferred**：晋升功能（含本表）随销售管理整体转入后续范围，**当前不建表、不实现读写路径**。下面保留概念讲解，作为未来实现基线（详见 `04-数据模型设计.md` §16.2）。

**用途**：记录销售每次等级调整的完整历史。每次晋升/降级追加一条记录，不覆盖当前值。

| 字段 | 中文 | 业务含义 |
|------|------|----------|
| `history_id` | 记录ID | UUID |
| `user_id` | 被调整的销售 | - |
| `from_tier` | 原等级 | A/SA/MA |
| `to_tier` | 新等级 | A/SA/MA |
| `changed_at` | 变更时间 | 精确到秒，用于划分"晋升前/后"的客户归属 |
| `changed_by` | 操作人 | 未来由哪个 Strategic 操作 |
| `reason` | 原因 | 如"季度晋升" |

### 2.1c `handover_request` — 未来复杂离职审批/交接请求（Deferred，暂不做）

> **Deferred**：只有未来引入申请、审批、逐客户交接和 SLA 时才考虑本表。当前 Strategic 直接离职回池不创建本表，User/Session/Assignment/Lead/Audit/Outbox 在一个事务完成。

**用途**：每个离职销售生成一条交接记录，追踪进度直到全部客户重新分配。

| 字段 | 中文 | 业务含义 |
|------|------|----------|
| `handover_id` | 交接ID | UUID |
| `user_id` | 离职销售 | - |
| `reviewer_user_id` | 未来审批/交接负责人 | Strategic 用户 |
| `total_customers` | 待交接客户数 | - |
| `completed_count` | 已完成数 | 每完成一个就 +1 |
| `status` | 状态 | pending_handover → in_progress → complete |
| `sla_due_at` | 截止时间 | 创建时间 + 3 工作日 |
| `completed_at` | 完成时间 | - |

### 2.2 `auth_session` — 登录会话

**用途**：记录每一次登录。登出、过期、被踢都能追踪。

| 字段 | 中文 | 业务含义 |
|------|------|----------|
| `session_id` | 会话ID | 服务端生成的会话标识 |
| `user_id` | 所属用户 | 这个会话是谁的 |
| `refresh_token_hash` | 刷新令牌哈希 | 只存 Hash，不存明文 Token，防止泄露被用来伪造登录 |
| `issued_token_version` | 签发时的Token版本 | 创建会话时用户的 token_version。用于判断会话是否因全局踢下线而失效 |
| `ip_address` | 来源IP | 从哪登录的 |
| `user_agent` | 浏览器信息 | 用什么设备和浏览器 |
| `expires_at` | 过期时间 | 会话什么时候自动过期 |
| `revoked_at` | 撤销时间 | 手动登出或 Strategic 执行安全操作的时间 |
| `revoke_reason` | 撤销原因 | logout=自己登出、disabled=被禁用、departed=离职、security=安全原因 |
| `last_seen_at` | 最近活跃时间 | 最后一次发起请求的时间 |
| `created_at` | 创建时间 | 什么时候登录的 |

### 2.3 `ref_region_country` — 区域-国家对照表（v3.5 新增）

**用途**：一张"参考数据表"，类似字典：记录 6 个大区（NA/EA/SEA/EU/ME/OTHER）下 205 个国家/地区的归属。来自"区域国家对照与分配规则表 v5"，由 `db/seeds/0001_region_country_v5.sql` 整体导入，换版时整体替换。Seed 可重复执行，并会先校验 205 条/6 区；源表中的 `7` 占位被明确规范化为 NULL，时区备注不混入 IANA 值。

| 字段 | 中文 | 业务含义 |
|------|------|----------|
| `country_code` | 国家代码 | 主键，ISO 3166-1 alpha-2（科索沃用 XK） |
| `country_name` | 国家名 | 中文名 |
| `region_code` | 所属大区 | NA/EA/SEA/EU/ME/OTHER |
| `subregion` | 子区域 | 仅参考，不参与分配 |
| `default_timezone` | 默认时区 | IANA 时区 |
| `data_version` | 对照表版本 | 如 region-country-v5 |

⚡ **关键规则**：
- 归 IAM 拥有，其他模块通过 `RegionCountryReadPort` **只读**使用，谁也不能写
- 候选、公司的 `country_code`/`region_code` 归一化以本表为准；不建外键（换版时整体替换，避免阻塞），靠 ACL 和集成测试保证一致
- 候选、公司和 Sales Lead 都保存实际使用的映射版本；参考表换版后，历史池归属仍能说明“当时为什么分到这里”

## 三、Task Runtime（任务运行时）— 8 张表

这些表不是业务表，它们是支撑所有"异步执行"的基础设施。

### 3.1 `job` — 异步任务

**用途**：所有长任务（搜索、LLM 调用、邮件发送、会议处理）的统一任务记录。相当于一个"任务调度器"。

| 字段 | 中文 | 业务含义 |
|------|------|----------|
| `job_id` | 任务ID | 每个异步操作的唯一标识，返回给前端用于查询进度 |
| `job_type` | 任务类型 | 带版本号，如 `lead.search_pipeline.v1`。不同版本可能行为不同 |
| `queue_name` | 队列名 | 任务进哪个队列：lead=线索、analysis=分析、mail=邮件、media=媒体、event=事件、data=数据补全（v3.5新增）、llm=LLM 调用（v3.5新增） |
| `aggregate_type` | 关联聚合类型 | 这个 Job 关联哪个业务对象类型，如 lead_candidate、analysis_run |
| `aggregate_id` | 关联聚合ID | 这个 Job 关联哪个具体业务对象 |
| `concurrency_key` | 单活键 | 需要单资源单活时写确定性键，如 `meeting:{meeting_id}:process`；active 状态下数据库唯一 |
| `retry_of_job_id` | 来自哪个旧Job | 人工重试时，新建一个 Job，指向旧 Job。旧 Job 保持终态不复活 |
| `status` | 状态 | queued→running→succeeded/failed。详见下文状态流转 |
| `priority` | 优先级 | 0-1000，越小越优先执行 |
| `payload` | 任务输入 | 执行这个任务需要什么参数，存 JSON |
| `result_summary` | 结果摘要 | 任务完成后保存简要结果，脱敏的 |
| `progress_percent` | 进度百分比 | 0-100，从 progress_event 中取最大值 |
| `attempt_count` | 已执行次数 | 包括失败重试，从 job_attempt 表计数得来 |
| `max_attempts` | 最大重试次数 | 超过这个次数就 failed_final，不再重试 |
| `run_after` | 最早执行时间 | 任务至少要等到这个时间才能被 Worker 领取 |
| `locked_by` | 执行者 | 哪个 Worker 领取了这个任务 |
| `lock_token` | 租约令牌 | 防多个 Worker 同时执行同一个任务的"钥匙" |
| `locked_until` | 租约过期时间 | Worker 必须在此之前续约，否则被其他 Worker 抢占 |
| `last_error_code` | 最后错误码 | 最后一次失败的错误码 |
| `last_error_message` | 最后错误信息 | 脱敏的错误描述 |
| `correlation_id` | 链路ID | 关联多个 Job 的追踪 ID |
| `created_by` | 发起人 | 谁触发的这个任务 |
| `created_at` | 创建时间 | - |
| `started_at` | 首次开始时间 | - |
| `completed_at` | 终态时间 | - |
| `version` | 乐观锁版本 | - |

⚡ **状态流转**：

```
queued → running → succeeded
                → retry_wait → running（重试）
                → failed_final（不再重试）
                → reconcile_required（外部结果不确定，需人工对账）
queued → cancelled
dead（策略标记的终态）
```

**关键设计**：人工重试不复活旧 Job。新建一个 Job 指向旧 Job 即可，旧 Job 永远保留当时的技术历史。Search Run、Candidate Refresh、Analysis、Meeting、Manual Note 和同类数据补全使用 `concurrency_key` 的 active 部分唯一索引，数据库直接阻止同一资源出现两个活跃 Job。

### 3.2 `job_attempt` — 任务执行记录

**用途**：每次 Job 被执行（包括重试）的详细技术记录。Worker 写了什么、Provider 回了什么、花了多少钱。

| 字段 | 中文 | 业务含义 |
|------|------|----------|
| `attempt_id` | 执行记录ID | - |
| `job_id` | 所属Job | - |
| `attempt_no` | 第几次 | 同个 Job 的第几次执行，从 1 开始 |
| `worker_id` | Worker标识 | - |
| `lock_token` | 本次租约令牌 | - |
| `status` | 结果 | started/succeeded/failed/lease_lost（租约丢了） |
| `provider_code` | 主Provider | 如 openai、anthropic、sendgrid |
| `provider_request_id` | 主请求ID | 用于排查外部问题 |
| `request_summary` | 请求摘要 | 脱敏后的请求内容 |
| `response_summary` | 响应摘要 | 脱敏后的响应内容 |
| `metrics` | 用量指标 | Token 数、延迟、成本。固定 JSON 结构，金额必须用十进制定点字符串 |
| `error_code` | 错误码 | - |
| `error_message` | 错误信息 | 脱敏 |
| `started_at` | 开始时间 | - |
| `completed_at` | 完成时间 | - |

⚡ **metrics 结构**（每次 Attempt 一台账）：

```json
{
  "input_tokens": 1200,
  "output_tokens": 350,
  "cached_input_tokens": 0,
  "total_tokens": 1550,
  "latency_ms": 842,
  "cost_amount": "0.012345",
  "currency": "USD",
  "cost_status": "confirmed"
}
```

`total_tokens` 必须等于 `input_tokens + output_tokens`。金额用字符串防浮点精度问题。

### 3.3 `job_progress_event` — 任务进度事件

**用途**：前端通过 SSE 实时看到"搜索中、已找到 5 家公司、正在评分..."。每一条事件都有递增的 Event ID，断网重连也不丢。

| 字段 | 中文 | 业务含义 |
|------|------|----------|
| `progress_event_id` | 事件ID | 自增数字，SSE 的 Event ID |
| `job_id` | 所属Job | - |
| `sequence_no` | 顺序号 | Job 内的递增序号 |
| `event_type` | 事件类型 | progress=进度更新、step=步骤变化、candidate=找到了候选、error=出错、completed=完成 |
| `step_code` | 步骤代码 | search/extract/enrich/score/scale 等，前端可以据此展示不同图标 |
| `progress_percent` | 进度百分比 | 0-100 |
| `message` | 消息 | 给人看的文本，如"正在搜索第3页..." |
| `payload` | 附加数据 | 如发现的候选简要信息、统计数字 |
| `created_at` | 时间 | - |

⚡ **注意**：这里不保存模型的原始输出。只保存"总结性"进度和决策结果。

### 3.4 `idempotency_record` — 幂等记录

**用途**：防止同一个操作被执行两次。比如用户网络卡了连点两次"认领"，第二次会直接返回第一次的结果而不会重复创建 Assignment。

| 字段 | 中文 | 业务含义 |
|------|------|----------|
| `idempotency_id` | 记录ID | - |
| `scope` | 幂等范围 | 如 candidate_select、lead_claim、meeting_upload |
| `principal_type` | 主体类型 | user=用户请求、event_consumer=事件消费者、system=系统 |
| `principal_id` | 主体ID | 用户ID 或 Consumer 名字 |
| `actor_user_id` | 操作人 | - |
| `idempotency_key` | 幂等键 | 客户端生成每次操作唯一的值；Consumer 用 event_id |
| `request_hash` | 请求内容哈希 | SHA-256(请求体)。键相同但内容不同就报冲突 |
| `state` | 执行状态 | in_progress/completed/failed |
| `resource_type` | 结果资源类型 | - |
| `resource_id` | 结果资源ID | 创建的 Company/Lead 等的 ID |
| `response_status` | 响应状态码 | 100-599 |
| `response_body` | 可重放的响应体 | 相同请求直接返回这个 |
| `expires_at` | 过期时间 | 幂等记录不永久保存，过一段时间清理 |
| `created_at` | 创建时间 | - |
| `updated_at` | 更新时间 | - |

⚡ **Power**：scope + principal_type + principal_id + idempotency_key **四个一起唯一**。相同组合第二次来就直接返回第一次的结果。

### 3.5 `outbox_event` — 发件箱事件

**用途**：数据库事务提交后发布事件。解决了"存了数据但没发出消息"或"发了消息但没存数据"的问题。事件和业务数据在同一个数据库事务中写入。

| 字段 | 中文 | 业务含义 |
|------|------|----------|
| `event_id` | 事件ID | - |
| `event_type` | 事件类型 | 带版本号，如 `crm.lead_assigned.v1` |
| `schema_version` | Payload格式版本 | - |
| `producer` | 发布模块 | 如 sales_crm |
| `aggregate_type` | 聚合类型 | 如 sales_lead |
| `aggregate_id` | 聚合ID | - |
| `aggregate_version` | 聚合版本 | 产生事件时聚合的版本号 |
| `payload` | 事件数据 | - |
| `headers` | 事件头 | Trace ID、Actor 信息 |
| `status` | 投递状态 | pending→processing→published（全部必需Consumer都已成功）→dead（投递失败） |
| `available_at` | 可投递时间 | - |
| `attempt_count` | 投递次数 | - |
| `locked_by` | 领取者 | Dispatcher Worker |
| `lock_token` | 租约 | - |
| `locked_until` | 租约过期 | - |
| `published_at` | 发布完成时间 | - |
| `last_error` | 最后错误 | - |
| `correlation_id` | 链路ID | - |
| `causation_id` | 原因事件ID | 如果事件B是由事件A触发的，这里记录事件A的ID |
| `created_at` | 创建时间 | - |

⚡ **关键设计**：Outbox 和业务数据在同一个 PostgreSQL 事务中提交——要么都成功，要么都回滚。不存在"数据写了但事件丢了"的情况。

### 3.6 `external_event` — 外部事件

**用途**：接收外部回调（如邮件发送状态的 Webhook），验签后存入，然后由 Dispatcher 路由处理。

## 八、为什么这样设计——常见问题解答

### Q1：为什么 ICP 和 Scale 分开两张表？

因为它们是两个不同的问题。ICP 回答"这家公司跟我们的业务匹配吗？"，Scale 回答"这家公司大不大，该进 MA/SA/A 哪个池？"。

一个低匹配度的大公司（如大型传统银行）可能是 D 级 ICP 但 large Scale。一个高匹配度的小公司可能是 A 级 ICP 但 small Scale。两者必须独立评估。

### Q2：为什么要 Candidate Contact 和 Contact 两张表？

Candidate 是还没入池的"潜在候选"，Contact 是已经入池的"正式联系人"。

候选阶段可能发现 10 个联系人，但入池时可能只晋升其中 3 个最关键的。Candidate Contact 保留搜索历史，Contact 是运营基础。

### Q3：为什么 Job 重试不复活而是新建？

因为旧 Job 的 attempt 历史、错误信息、时间线是"真实发生过的事实"，不应该被改写。新建 Retry Job 并指向旧 Job，既能追溯到原始失败原因，又能保留新 Job 的独立执行历史。

### Q4：为什么要这么多"反规范化列"？

像 `sales_lead.current_owner_user_id` 这样的列需要从 `lead_assignment` 推导，但"列出我所有的线索"这种查询每天要跑很多次。如果每次都要 JOIN + 排序 + 取最新，太慢。所以我们在 Assignment 写入时同步更新这个列，查询时直接读。

但反规范化不是"想存就存"。每一列都有明确的来源表、同步时机、同步方式，并且在 §17 反规范化登记中有完整记录。

### Q5：为什么不用 Redis、Kafka、Elasticsearch？

当前团队规模和技术栈一致（Python/FastAPI/PostgreSQL），引入更多中间件会增加运维负担、排查难度和学习成本。PostgreSQL 的 Lease Queue（FOR UPDATE SKIP LOCKED）和 Outbox 模式可以可靠地承载当前的异步任务量。

未来如果确实遇到瓶颈，可以在这些成熟的扩展点引入新的中间件——但不是现在。

### Q6：为什么"每 Company 最多一个未关闭 Sales Lead"？

这是销售资源管理的核心约束。如果一个公司可以同时有两条活跃销售线索，就会出现两个销售同时跟进同一家公司、互相不知道对方在做什么的情况。

如果公司确实需要重新跟进（比如之前 lost 了，现在又能做了），就关闭旧的 Sales Lead，创建新的。Company 本身保留不删，可以跨多个销售周期使用。

### Q7：前端能计算 Grade、Tier 或 Owner 吗？

**绝对不能。** 这些是后端领域逻辑。前端如果自己在浏览器里算一遍，就会出现"前端显示 A 级 → 认领被拒（实际是 B 级）→ 用户困惑"的情况。

前端只能展示后端返回的值，不应做任何业务判断。

## 九、Deferred：已确认但延期的能力（v3.6 登记）

下面这些能力已经讨论过、有设计基线，但**当前版本明确不做**。写代码时别顺手实现，也别在表里预留读写路径。

### 9.1 完整销售管理（当前只延期复杂部分）
