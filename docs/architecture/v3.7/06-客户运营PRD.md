# 06 - 客户运营 PRD

> 版本：v3.7  
> 模块：Customer Operation  
> 重构方向：围绕客户沟通闭环，而不是围绕单个 Agent 或零散接口  
> 当前实现基线：真实邮箱 SMTP 发信、IMAP 收信、邮件入库、监控邮箱配置入库已经可用

---

## 1. 背景

客户运营模块的核心价值不是“能发邮件”或“能上传会议录音”，而是帮助销售围绕客户持续推进沟通：知道客户是谁、该说什么、是否已经发出、客户有没有回复、回复表达了什么意图、下一步该做什么，以及所有沟通过程是否沉淀到客户动态里。

因此本版 PRD 按照一条完整业务主线重构：

```text
客户档案 -> 生成邮件 -> 发信 -> 收信/回信 -> 识别意图 -> 生成跟进任务 -> 更新客户动态
```

会议、任务、手动记录、客户活动都围绕这条主线服务，而不是作为孤立功能存在。

---

## 2. 目标

### 2.1 产品目标

1. 销售可以基于客户档案和历史沟通生成一封可编辑的跟进邮件。
2. 平台可以通过真实邮箱发送邮件，并把发送结果写入数据库。
3. 系统可以监控多个真实邮箱，收到客户回信后自动入库。
4. 系统可以识别客户回复意图，并给出下一步动作。
5. 系统可以把邮件、会议、任务、手动记录统一沉淀为客户运营历史。
6. 销售可以在客户详情页看到完整沟通脉络，而不是分散查看邮件、会议和任务。

### 2.2 当前阶段目标

当前阶段优先打通“邮件沟通闭环”，会议、任务、客户活动作为同一闭环的承接能力逐步补齐。

已具备的能力：

- SMTP 真实发信
- IMAP 真实收信
- 多邮箱监控配置
- 邮件收发入库
- 发信投递记录入库
- 邮件附件元数据入库

仍需产品化补齐的能力：

- 邮件回复自动意图识别并回写 `email_message`
- 根据意图自动创建 `follow_up_task`
- 邮件、会议、任务统一生成 `customer_activity`
- 客户详情页按时间线展示完整沟通历史
- 会议分析结果进入同一客户运营闭环

## 3. 用户角色

| 角色 | 需求 |
|---|---|
| 销售 | 快速写出合适的客户邮件，知道客户有没有回复，知道下一步做什么 |
| 销售主管 | 查看客户推进状态，判断销售是否持续跟进 |
| 运营/管理员 | 配置监控邮箱，排查收发失败，保证邮件链路可用 |
| 系统 | 自动沉淀沟通事实，减少人工录入 |

## 4. 核心业务闭环

### 4.1 客户档案

客户运营从客户档案开始。系统至少需要知道：

- 公司：`company`
- 联系人：`contact`
- 历史邮件：`email_message`
- 历史会议：`meeting`
- 待办任务：`follow_up_task`
- 客户动态：`customer_activity`

客户档案不是静态资料，而是后续生成邮件、判断意图、安排任务的上下文来源。

### 4.1b 销售首次触达线索

销售第一次收到线索，通常来自两种情况：

- 销售主动认领线索
- 系统或主管把线索分配给销售

这时客户运营模块要把“新线索”转成“可沟通对象”，并推动销售完成首次触达。

首次触达流程：

```text
销售收到/认领线索 -> 查看客户档案 -> 选择联系人 -> 生成首次触达邮件 -> 销售编辑确认 -> 发信 -> 更新客户状态 -> 写入客户动态
```

系统需要读取：

- `company`：公司名称、官网、行业、地区、简介等
- `contact`：联系人姓名、职位、邮箱、优先级等
- `sales_lead`：线索阶段、归属销售、当前推进状态
- 可选的客户分析报告：市场、公司、竞品、产品建议等上下文

首次触达邮件发送成功后：

- 写入 `email_message(direction='outbound', purpose='first_touch')`
- 写入 `email_delivery_attempt`
- 将客户或线索推进状态更新为 `emailed`
- 写入客户动态：首次触达邮件已发送
- 后续如果客户回信，进入“收信/回信 -> 识别意图 -> 生成跟进任务”的闭环

这个场景是客户运营的起点。没有首次触达，后续回信识别、会议、任务和客户动态都没有稳定的业务入口。

### 4.2 生成邮件

销售在客户详情页选择联系人，点击生成邮件。

系统读取：

- 公司基本信息
- 联系人信息
- 最近邮件往来
- 最近会议摘要
- 未完成跟进任务
- 可选的客户分析报告

输出：

- 邮件主题
- 邮件正文
- 邮件用途：首次触达、回复跟进、会后跟进
- 推荐语气和下一步目标

销售可以编辑邮件后再发送。

### 4.3 发信

销售点击发送后，系统通过 SMTP 发送真实邮件。

成功后写入：

- `email_message(direction='outbound')`
- `email_delivery_attempt`
- 有附件时写入 `media_asset` 和 `email_attachment`

发信成功不代表客户已回复，只代表这次触达已经发生。

### 4.4 收信/回信

系统从 `mailbox_monitor` 读取启用的邮箱配置，通过 IMAP 定时轮询。

收到新邮件后：

1. 解析发件人、收件人、主题、正文、Message-ID、In-Reply-To。
2. 根据发件人邮箱匹配或创建 `contact`。
3. 根据联系人归属匹配或创建 `company`。
4. 写入 `email_message(direction='inbound')`。
5. 如果是回复邮件，通过 `parent_email_id`、`thread_key`、`in_reply_to` 串成邮件线程。

### 4.5 识别意图

系统对入站邮件进行意图识别。

意图类型：

| 意图 | 含义 | 后续动作 |
|---|---|---|
| `interested` | 客户有兴趣 | 创建会议或进一步沟通任务 |
| `pricing` | 询价 | 创建报价/价格说明任务 |
| `product_question` | 产品问题 | 创建产品答疑任务 |
| `not_interested` | 暂无兴趣 | 降低优先级或暂停跟进 |
| `unsubscribe` | 退订/拒收 | 写入退订名单并停止触达 |

识别结果写回：

- `email_message.intent_level`
- `email_message.intent_payload`
- `email_message.next_action`

### 4.6 生成跟进任务

当客户回复表达积极意图或需要动作时，系统创建 `follow_up_task`。

任务来源可以是：

- 邮件：`source_email_id`
- 会议：`source_meeting_id`
- 报告：`source_report_id`
- 异步任务：`source_job_id`

任务类型：

- 邮件跟进
- 电话沟通
- 安排会议
- 发送方案
- 数据补全
- 其他

### 4.7 更新客户动态

客户动态是销售查看客户推进历史的统一入口。

邮件、会议、任务、手动备注不应只留在各自表里，还需要转成客户时间线事实，例如：

- 已发送邮件
- 收到客户回复
- 客户询价
- 完成会议
- 生成会后待办
- 销售手动记录关键情况

当前 `customer_activity` 表的类型还比较泛，后续需要扩展或通过 `payload` 保留来源细节。

## 5. 功能需求

### 5.1 客户运营总览

客户详情页需要展示：

- 公司和联系人信息
- 最近一次邮件
- 最近一次客户回信
- 最近一次会议
- 未完成跟进任务
- 客户运营时间线

验收标准：

- 能按公司查看邮件、会议、任务和动态
- 时间线按发生时间倒序
- 每条记录能看出来源和下一步动作

### 5.2 邮件生成

销售可以生成以下类型邮件：

- 首次触达
- 回复跟进
- 会后跟进

输入：

- 客户 ID
- 联系人 ID
- 邮件目的
- 销售补充要求

输出：

- 主题
- 正文
- 生成模型
- prompt 版本

验收标准：

- 邮件内容能引用客户上下文
- 销售可编辑后发送
- 生成记录能追溯 prompt 版本和模型

### 5.2b 首次触达

当销售第一次收到或认领线索后，系统需要支持直接从客户详情页发起首次触达。

输入：

- 公司 ID
- 线索 ID
- 联系人 ID
- 邮件目的固定为 `first_touch`
- 销售补充要求

输出：

- 首次触达邮件主题
- 首次触达邮件正文
- 推荐下一步目标

业务规则：

- 如果客户没有联系人邮箱，系统提示先补全联系人邮箱
- 如果同一联系人已经存在近期首次触达邮件，系统提示销售确认，避免重复触达
- 首次触达邮件发送成功后，邮件 `purpose` 必须为 `first_touch`
- 首次触达邮件发送成功后，客户或线索状态进入 `emailed`
- 首次触达动作必须写入客户动态

验收标准：

- 销售认领或收到线索后，可以直接生成首次触达邮件
- 发送成功后能在 `email_message` 查到 `purpose='first_touch'`
- 发送成功后客户运营总览能看到“首次触达已发送”
- 如果客户后续回信，系统能继续进入意图识别和任务生成流程

### 5.3 邮件发送

系统通过 SMTP 发送真实邮件。

发送成功后：

- 写入 `email_message`
- 写入 `email_delivery_attempt`
- 返回发送结果

发送失败后：

- 返回明确错误
- 记录失败原因
- 不应错误地标记为已发送

验收标准：

- 发信接口返回成功后，数据库能查到 outbound 邮件
- `email_delivery_attempt` 能查到本次投递尝试
- 附件能通过 `media_asset` 和 `email_attachment` 追溯

### 5.4 邮箱监控

管理员可以配置多个监控邮箱。

每个监控邮箱包括：

- 邮箱账号
- IMAP host
- IMAP port
- 授权码/密码
- 邮箱目录
- 是否启用
- 轮询间隔

当前密码/授权码保存在 `mailbox_monitor.secret_value`。

验收标准：

- `/api/inbound-mail/monitors` 能看到启用监控邮箱
- `/api/inbound-mail/poll-now` 能触发所有启用邮箱轮询
- 单个邮箱失败不能影响其他邮箱继续轮询

### 5.5 收信入库

系统轮询到新邮件后，需要写入 `email_message(direction='inbound')`。

验收标准：

- 发件人、收件人、主题、正文、收到时间正确入库
- 能根据 Message-ID / In-Reply-To 串联回复关系
- 同一封邮件不能重复入库

### 5.6 回复意图识别

系统对客户回信进行意图识别，并给出下一步动作。

验收标准：

- `pricing` 类回复能生成报价跟进任务
- `interested` 类回复能生成会议或沟通任务
- `unsubscribe` 类回复能进入退订/屏蔽逻辑
- 识别结果能回写邮件记录

### 5.7 会议处理

销售可以上传会议录音或导入会议记录。

系统处理流程：

```text
上传会议文件 -> 保存媒体资源 -> 转写 -> 摘要 -> 提取 action_items / next_step -> 生成跟进任务 -> 更新客户动态
```

会议结果需要写入：

- `media_asset`
- `meeting`
- `meeting_segment`
- `follow_up_task`
- `customer_activity`

验收标准：

- 会议处理完成后能看到摘要、决策、风险、关键词和下一步
- action items 能生成任务
- 会议能出现在客户运营时间线中

### 5.8 跟进任务

任务用于承接邮件和会议产生的下一步动作。

任务字段包括：

- 标题
- 类型
- 描述
- 截止时间
- 优先级
- 状态
- 来源对象

任务状态：

```text
pending -> in_progress -> completed
pending -> cancelled
```

验收标准：

- 客户回信和会议摘要都能创建任务
- 销售可以完成或取消任务
- 任务完成后客户动态能体现

### 5.9 客户活动

客户活动是统一时间线。

应覆盖：

- 邮件发送
- 邮件回复
- 意图识别
- 会议完成
- 任务创建
- 任务完成
- 手动备注

验收标准：

- 销售不用分别进入邮件、会议、任务列表，也能看到客户推进历史
- 每条活动都能追溯来源

## 7. 状态流转

### 7.1 邮件状态

发信：

```text
draft -> approved -> queued -> sending -> sent -> delivered
                                    -> failed
delivered -> replied
```

收信：

```text
received -> processing -> processed
                     -> failed
```

### 7.2 客户推进状态

客户运营会影响销售线索或客户阶段：

```text
assigned -> first_touch_ready -> emailed -> replied -> meeting -> proposal -> won/lost
```

说明：

- 销售收到或认领线索后进入 `first_touch_ready`
- 发信成功后可进入 `emailed`
- 客户有效回信后进入 `replied`
- 安排或完成会议后进入 `meeting`
- 发送方案后进入 `proposal`

### 7.3 任务状态

```text
pending -> in_progress -> completed
pending -> cancelled
```

## 9. 异常和降级

### 9.1 发信失败

- SMTP 失败时返回错误
- `email_delivery_attempt.status='failed'`
- 邮件不能标记为 `sent`
- 后续可加入重试任务

### 9.2 收信失败

- 单个邮箱失败不影响其他邮箱
- 错误返回到 `/api/inbound-mail/poll-now.errors`
- 后续需要把错误写入监控日志或任务表

### 9.3 意图识别失败

- 邮件仍然保留 `received`
- 标记为待人工处理
- 不自动生成任务

### 9.4 会议分析失败

- 保留原始音频
- 标记会议处理失败
- 允许重新处理或人工上传转写文本

## 10. 验收标准

### 10.0 首次触达闭环

1. 销售收到或认领线索后，能在客户运营入口看到该客户。
2. 销售能基于公司、联系人和线索上下文生成首次触达邮件。
3. 首次触达邮件发送成功后，数据库有 `purpose='first_touch'` 的 outbound 邮件。
4. 首次触达邮件发送成功后，客户或线索状态进入 `emailed`。
5. 客户动态中能看到“首次触达邮件已发送”。
6. 客户回信后，能继续进入收信、意图识别和跟进任务流程。

### 10.1 邮件闭环

1. 平台能发出真实邮件。
2. 发信后数据库有 outbound 邮件。
3. 投递尝试能在 `email_delivery_attempt` 查询。
4. 真实邮箱收到客户回信后，IMAP 能拉取。
5. 收信后数据库有 inbound 邮件。
6. 回信能尽量串到原邮件线程。
7. 有效回信能生成下一步任务。

### 10.2 会议闭环

1. 销售能上传会议文件。
2. 系统能保存音频资源。
3. 系统能生成转写和摘要。
4. 摘要中的 action items 能生成任务。
5. 会议结果能进入客户时间线。

### 10.3 任务闭环

1. 任务能从邮件或会议自动创建。
2. 销售能看到待办任务。
3. 销售能完成或取消任务。
4. 任务状态变化能进入客户动态。

### 10.4 客户动态闭环

1. 客户详情页能按时间线展示邮件、会议、任务和备注。
2. 每条动态能追溯来源。
3. 销售能从动态直接判断下一步动作。

## 11. 本版边界

本版包含：

- 邮件收发
- 邮箱监控
- 邮件意图识别
- 会议处理
- 跟进任务
- 客户活动
- 手动备注

本版暂不包含：

- 完整权限体系
- 邮箱密码加密存储
- 邮件打开率/点击率追踪
- 完整营销 Campaign 编排
- 多销售协作审批流
- 复杂 SLA 自动升级

---

## 12. 推荐实施顺序

1. 稳定邮件收发和入库链路。
2. 把入站邮件接入意图识别。
3. 根据意图自动创建 `follow_up_task`。
4. 邮件事件写入 `customer_activity`。
5. 会议处理结果写入正式 PostgreSQL 表。
6. 会议 action items 生成任务。
7. 客户详情页统一展示时间线。
8. 补齐监控邮箱管理界面和失败日志。

---

## 13. 一句话总结

客户运营模块的目标是把每一次客户沟通都变成可追踪、可判断、可推进的业务事实：系统知道发了什么、客户回了什么、客户想要什么、销售下一步该做什么，并把这些都沉淀到同一个客户时间线里。
